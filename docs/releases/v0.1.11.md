# Ludo Club v0.1.11

Hold-to-speak now attempts live room audio over a separate authenticated
WebSocket. Opus encoding and decoding run in a browser worker, with microphone
capture on the audio rendering thread. One person speaks live at a time; live
media is not saved or written to SQLite.

The existing voice-message architecture remains the fallback. If a listener's
browser cannot play live audio, playback is locked, or a live transmission is
interrupted or unacknowledged, release sends the complete recording instead.
Users can also choose voice notes explicitly in the game menu. Holds remain
limited to 60 seconds, and saved recordings retain their 1-MiB limit and existing
retention policy. Speech already heard live cannot be retracted by cancellation.

Live transport has independent connection/control/frame limits, one receiving
tab per guest, bounded send/playback queues, room membership and block checks,
and reconnect backoff. Leaving a room revokes all of that guest's audio tabs.
Speaker mute and the muted-speaker notice cover both live audio and voice notes.
`LIVE_VOICE_ENABLED=false` disables live upgrades while preserving recorded voice.

The relay uses the ordinary HTTPS/WebSocket route, without Coturn or new public
UDP ports. It performs no media transcoding. Streaming audio avoids room-state
broadcasts and database work; SQLite still requires one authoritative app replica.
TCP retransmission delays remain possible on poor networks.

This release also fixes WebKit dialog keyboard containment and Settings focus
restoration. Browser test runs now isolate each engine's server so production
room-creation quotas remain intact during local cross-browser validation.

Validation includes 133 automated tests, Chromium/Firefox/WebKit suites, live
playback before release, mute, interrupted-delivery fallback, room isolation,
all-tab revocation and malformed-input checks. Both architecture image smoke
gates now exercise the actual live-audio WebSocket relay. The documented local
20-room/80-guest relay run delivered all expected recipient frames alongside chat;
it is a short synthetic test, not a production capacity guarantee. Physical
Android/iPhone audio quality and tunnel latency remain manual acceptance checks.

See [the live voice design and benchmark](../LIVE_VOICE.md) for protocol,
privacy, scaling and validation details. No game-state schema migration is needed.
